3. 接入方案对比

方案做法优点缺点 / 风险
A 纯独立浏览页：导航加「品牌」「型号」两个 tab，页面只负责浏览与跳转 几乎不动现有代码，新增 2 个文件 + main.py 3 处挂载 点了卡片之后「发生什么」不明确，容易变成死页
B 改造为选择器页：把现有 QComboBox 换成「选择品牌…」按钮，点开整页，选完自动返回并预填 交互最接近参考图，下拉彻底消灭 影响面最大：model_page.py、bracket_page.py、entry_forms.py 三处下拉都要改；要维护「从哪来、回哪去」的状态，回归风险高
C 推荐 独立页 + 点选跳转：新增两页进导航，点品牌卡片 → 切到「按车型查」并预填该品牌、自动加载车型；点型号卡片 → 切到「按支架查」并预填支架号。现有下拉原样保留 新增为主、不改存量；两页有明确用途；下拉仍可快手输入；回退容易 同一件事有两条入口（卡片 + 下拉），需要文案区分；导航从 3 个变 5 个
推荐 C 的理由：本项目现有下拉已经带拼音补全，熟练用户靠键盘更快；卡片页解决的是「不知道该选哪个、想看全貌」的场景。两者互补而非替代，且新增两个文件不触碰既有逻辑，出问题可单独摘掉。

7. 数据与性能

7.1 数据来源（已存在，无需改库）

brands(brand PRIMARY KEY, logo_url, logo_file, updated_at)     → 269 行
models(brand, model, PRIMARY KEY(brand, model))
brackets(bracket_id PRIMARY KEY, image_url, image_file, updated_at)
fitments(... brand, model, years_raw ...)
  • db.brands() 已返回 brand / logo_file / model_count，品牌页直接可用。
  • db.brackets() 已返回 bracket_id / image_file / fitment_count，型号页直接可用。
  • logo 文件名形如 brand_奥迪.jpg，路径由 config.image_path() 拼出。

7.2 分组规则

initials = search.keys(brand)[1]        # 全拼 + 首字母，见 search.py:44
group    = initials[:1].upper() if initials else "#"
if not ("A" <= group <= "Z"): group = "#"
  • 中文品牌 → 拼音首字母分组；英文/数字开头（ARCFOX极狐、212、iCAR）→ 归「#」组放最前或最后。
  • pypinyin 缺失时 search.keys 会降级为字面匹配，此时全部归「#」组，分组消失但不报错。

7.3 性能

关注点结论
269 张 logo 同时加载不能一次性全读。卡片用 ui.fill_plate(label, file, 40, 40)，即按需 40×40 缩放，且走 thumbs.pixmap 内存缓存；首屏只加载可见的十几张
首字母计算search._CHAR_CACHE 已有进程内缓存，269 个品牌只算一次
搜索响应search.filter_items 纯 Python 子串匹配，269 条可忽略；沿用现有 QTimer 防抖（若有）
滚动卡顿269 个 QFrame 一次性建会慢（约 200~400ms）。可选优化：分组懒加载，或只对可见区建卡（先不做，实测再定）
